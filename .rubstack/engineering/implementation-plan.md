# Implementation Plan

## Status

Lokalite v2.7.0 is the shipped Swift/macOS baseline. The active initiative is a
quality-gated replacement with full capability and security parity on macOS 14+
and Windows 11 (x64 and ARM64). It takes priority over new product features;
only critical fixes continue on the shipped Swift application while migration is
underway.

The shipped baseline remains the behavioral oracle: encrypted local storage,
projects and environments, import/export and backup/restore, CLI and MCP,
daemon-brokered access, agent governance, activity logging, the menu-bar app,
signed distribution, and in-app updates. Linux, mobile, cloud services,
accounts, synchronization, and team features are outside this initiative.

No automated test may use a production vault. The current Swift tests and
generated fixtures remain available until the replacement passes the final
cutover gate.

## Phase 0: Retire architectural risks

No domain port begins until all three prototypes pass. A failed gate changes the
architecture or scope before implementation continues.

### Task 0.1 — Prove vault and backup compatibility

**Goal**: Demonstrate that an independent Rust implementation can consume and
produce the shipped encrypted data formats without changing user data.

**Scope**: A disposable compatibility harness and synthetic golden fixtures for
the current vault schema, encrypted values, and encrypted backups.

**Acceptance criteria**:
- **Automated**: fixtures generated by the Swift baseline are read byte-for-byte
  correctly by the Rust prototype, and Swift reads the Rust-produced equivalents.
- **Manual**: fixture provenance, schema versions, and expected results are
  reviewed and recorded; no production vault or key is used.

### Task 0.2 — Prove the Windows desktop security boundary

**Goal**: Demonstrate that the proposed Windows desktop runtime can authenticate
the user and identify local broker clients within the required security model.

**Scope**: A disposable Windows 11 desktop prototype covering Windows Hello,
the application window boundary, local IPC ownership, peer-process attribution,
tray/background behavior, and single-instance behavior.

**Acceptance criteria**:
- **Automated**: Windows tests prove same-user IPC access, rejection of an
  unauthorized user, and reliable peer PID capture.
- **Manual**: on Windows 11, Windows Hello succeeds from the desktop app and
  fails closed when unavailable or cancelled; tray, background, and
  single-instance behavior work in an installed build.

### Task 0.3 — Prove Store-compatible delivery

**Goal**: Demonstrate that a Store-signed MSIX can deliver the desktop app and
independent command-line surfaces without a paid signing channel.

**Scope**: A disposable x64 and ARM64 MSIX prototype covering application
launch, the `lokalite` execution alias, CLI/MCP execution, app activation by a
client, autostart, and update constraints.

**Acceptance criteria**:
- **Automated**: CI produces installable x64 and ARM64 packages and validates
  their manifests and packaged executables.
- **Manual**: a Windows 11 installation proves app launch, CLI/MCP invocation,
  app activation, autostart behavior, and an update between two test versions.

**Prototype evidence (2026-07-29)**: cross-compilation and Microsoft's portable
MSIX SDK validate the x64 and ARM64 package layouts, including separate GUI and
console executables, the `lokalite.exe` execution alias, startup registration,
and the minimal declared capability. The CLI payload must be named
`lokalite-cli.exe` because package paths are case-insensitive and would collapse
`Lokalite.exe` with `lokalite.exe`. The portable SDK cannot emit a full embedded
bundle, and no local environment can exercise Windows package runtime behavior.
The task remains open until Windows SDK MakeAppx produces the full bundle and a
Windows 11 private Store flight passes installation, activation, alias,
autostart, update, ingestion, and Store-signing checks.

### Task 0.4 — Close the prototype gates

**Goal**: Produce an explicit go/no-go decision for the migration architecture.

**Scope**: Results and unresolved constraints from Tasks 0.1–0.3, reflected in
the relevant ADRs and feature specifications.

**Acceptance criteria**:
- **Automated**: every prototype check is reproducible from the repository's
  documented test commands.
- **Manual**: all three gates are marked passed, or the affected architecture is
  revised and the failed gate is repeated before Phase 1 starts.

**Depends on**: Tasks 0.1, 0.2, and 0.3.

## Phase 1: Establish the replacement workspace and contracts

### Task 1.1 — Create the Rust and desktop workspace

**Goal**: Establish a buildable workspace for the portable core, platform
adapters, service, CLI, MCP server, and Tauri desktop application.

**Scope**: Cargo workspace, React/TypeScript/Vite frontend, shared developer
commands, and macOS/Windows CI jobs.

**Acceptance criteria**:
- **Automated**: formatting, linting, type checking, unit tests, and empty
  release builds pass on macOS and Windows x64; Windows ARM64 is built wherever
  the CI platform permits it.
- **Manual**: a developer can launch the empty desktop shell, the independent
  `lokalite` CLI, and its `mcp` subcommand on each available target platform.

**Depends on**: Task 0.4.

### Task 1.2 — Freeze compatibility contracts

**Goal**: Make all behavior that existing users and integrations rely on
executable and versioned before it is ported.

**Scope**: Synthetic fixtures and contract cases for CLI commands and output,
MCP tools and protocol, IPC messages, schema versions, backups, context
resolution, and agent-governance outcomes.

**Acceptance criteria**:
- **Automated**: the Swift baseline passes the frozen contract suite and every
  contract fixture has an asserted expected result.
- **Manual**: the contract inventory is checked against existing user-facing
  documentation and representative macOS automation.

**Depends on**: Task 0.1.

### Task 1.3 — Define platform capability boundaries

**Goal**: Give portable code one stable contract for key storage,
authentication, local IPC, process attribution, clipboard, lifecycle, and
updates.

**Scope**: Shared platform interfaces and test doubles; no production platform
implementation.

**Acceptance criteria**:
- **Automated**: portable components compile and run their unit tests against
  test doubles without importing macOS or Windows APIs.
- **Manual**: every platform-dependent behavior in the frozen contract inventory
  has a named owner and an explicit fail-closed expectation where security is
  involved.

**Depends on**: Tasks 1.1 and 1.2.

## Phase 2: Port the portable vault core

### Task 2.1 — Port encrypted-value compatibility

**Goal**: Read and write existing vault ciphertext with no format or key change.

**Scope**: Portable vault encryption and decryption behavior.

**Acceptance criteria**:
- **Automated**: all Swift/Rust encrypted-value golden fixtures pass in both
  directions, including malformed and authentication-failure cases.
- **Manual**: the implementation is reviewed against ADR 0001 and the Phase 0
  compatibility evidence.

**Depends on**: Tasks 1.2 and 1.3.

### Task 2.2 — Port schema and storage behavior

**Goal**: Open the existing SQLite schema and preserve all persistence and
query behavior.

**Scope**: Portable database access, existing migrations, transactions, and
synthetic compatibility databases.

**Acceptance criteria**:
- **Automated**: every supported schema fixture opens without destructive
  change, the full storage suite passes, and a copied fixture is unchanged when
  no migration is required.
- **Manual**: schema inspection confirms that projects, environments, secrets,
  values, configuration, and activity entries survive an open/close cycle.

**Depends on**: Task 2.1.

### Task 2.3 — Port domain behavior

**Goal**: Match the shipped behavior for projects, environments, secrets,
context resolution, imports, exports, references, policies, and activity.

**Scope**: Portable domain and application-service behavior only.

**Acceptance criteria**:
- **Automated**: the frozen domain and compatibility suites pass against both
  the Swift oracle and Rust implementation with equivalent observable results.
- **Manual**: representative workflows are compared side by side without using
  a production vault.

**Depends on**: Task 2.2.

### Task 2.4 — Port backup and restore compatibility

**Goal**: Preserve encrypted backups as the supported transfer path between
macOS and Windows.

**Scope**: Existing encrypted backup envelope, restore semantics, and
cross-platform fixture coverage.

**Acceptance criteria**:
- **Automated**: Swift-generated backups restore in Rust, Rust-generated backups
  restore in Swift, and wrong-passphrase or damaged data fails without writes.
- **Manual**: a synthetic Active Environment backed up on one platform restores
  the same exported name/value set on the other, including the shipped
  approval-tier exclusion and skip-reporting behavior.

**Depends on**: Tasks 2.1 and 2.3.

## Phase 3: Rebuild the broker and platform security

### Task 3.1 — Version the broker protocol

**Goal**: Preserve current JSON behavior while allowing consecutive client and
daemon versions to negotiate safely.

**Scope**: Protocol envelope, handshake, compatibility errors, and fixtures for
the shipped unversioned client.

**Acceptance criteria**:
- **Automated**: new/new, old-client/new-daemon, and new-client/previous-daemon
  matrices produce the expected result or a clear incompatibility error; no
  client silently opens the vault locally.
- **Manual**: incompatibility messages tell the user which component must be
  updated without revealing vault data.

**Depends on**: Tasks 1.2 and 2.3.

### Task 3.2 — Rebuild the vault-owning service

**Goal**: Make the desktop application the sole owner of the vault key and the
single policy-enforcement chokepoint.

**Scope**: Service request handling, session lifecycle, approval coordination,
governance, and activity recording.

**Acceptance criteria**:
- **Automated**: concurrent service tests prove policy enforcement, fail-closed
  locked behavior, approval semantics, and activity records for reads and writes.
- **Manual**: inspection confirms CLI and MCP processes never load the vault key
  or open the database directly in normal operation.

**Depends on**: Tasks 2.3 and 3.1.

### Task 3.3 — Implement the macOS security adapter

**Goal**: Preserve the existing Keychain identity, LocalAuthentication behavior,
owner-only socket, and peer attribution on macOS 14+.

**Scope**: Production macOS key storage, authentication, local IPC, and process
identity adapters.

**Acceptance criteria**:
- **Automated**: adapter tests cover socket ownership, peer PID capture, key
  lookup identifiers, and fail-closed authentication outcomes.
- **Manual**: on macOS 14+, a synthetic copy of an existing vault unlocks with
  system authentication and broker activity shows the connecting process.

**Depends on**: Tasks 1.3 and 3.2.

### Task 3.4 — Implement the Windows security adapter

**Goal**: Protect each Windows vault key for the current user and require
Windows Hello for unlock and approval.

**Scope**: Production Windows key storage, desktop authentication, owner-only
local IPC, and peer attribution adapters.

**Acceptance criteria**:
- **Automated**: tests prove user-scoped key protection, same-user pipe access,
  peer PID capture, and fail-closed authentication outcomes on x64 and ARM64.
- **Manual**: Windows 11 face, fingerprint, or PIN unlock succeeds when
  configured; cancellation or unavailable Windows Hello never falls back to an
  application password or machine-scoped key.

**Depends on**: Tasks 0.2, 1.3, and 3.2.

## Phase 4: Reach CLI and MCP parity

### Task 4.1 — Port read and context CLI commands

**Goal**: Match shipped project/environment resolution and non-mutating CLI
behavior.

**Scope**: Read-only vault, project, environment, status, search, activity, and
context commands.

**Acceptance criteria**:
- **Automated**: command contracts match exit codes, stdout, stderr, and side
  effects for all frozen cases on macOS and Windows.
- **Manual**: representative existing scripts run unchanged against a synthetic
  vault on both platforms.

**Depends on**: Tasks 3.1–3.4.

### Task 4.2 — Port mutation and injection CLI commands

**Goal**: Match shipped create, update, delete, import, export, backup, restore,
clipboard, shell, subprocess injection, and agent-policy behavior.

**Scope**: Remaining CLI commands and daemon-mediated security behavior,
including unchanged POSIX `shell` output on macOS and PowerShell-default
`shell` output on Windows with `--shell powershell|posix|cmd`.

**Acceptance criteria**:
- **Automated**: frozen command and policy contracts pass on macOS and Windows,
  including denial and no-child-on-failure cases.
- **Manual**: hidden input, clipboard clearing, POSIX/PowerShell/cmd shell
  output, and subprocess injection are exercised on both platforms without
  exposing fixture values in logs or process arguments.

**Depends on**: Tasks 2.4 and 4.1.

### Task 4.3 — Port the MCP server

**Goal**: Preserve MCP tool names, inputs, outputs, handoff behavior, read/write
mode, protocol compatibility, and configuration semantics.

**Scope**: The independent `lokalite` binary's `mcp` subcommand and its daemon
client.

**Acceptance criteria**:
- **Automated**: the frozen MCP/JSON-RPC suite passes on macOS and Windows,
  including legacy configuration and every governance tier.
- **Manual**: a supported agent can use an unchanged existing configuration on
  macOS, and the equivalent Windows configuration completes list, read,
  environment-switch, and approved-write workflows.

**Depends on**: Tasks 3.2 and 4.1.

### Task 4.4 — Verify rolling command-line compatibility

**Goal**: Prove that supported mixed-version installations fail safely during
an update.

**Scope**: Previous/current CLI and MCP clients against previous/current
daemons on both platforms where applicable.

**Acceptance criteria**:
- **Automated**: the consecutive-version matrix passes in CI and asserts that no
  mismatch causes local vault fallback.
- **Manual**: user-facing upgrade guidance is understandable for every rejected
  combination.

**Depends on**: Tasks 3.1, 4.2, and 4.3.

## Phase 5: Reach desktop experience parity

### Task 5.1 — Build the shared visual shell

**Goal**: Reproduce Lokalite's current identity and navigation in the new
desktop application without redesigning the product.

**Scope**: React application shell, established colors, typography, category
semantics, layout, accessibility, and narrow desktop command boundary.

**Acceptance criteria**:
- **Automated**: frontend lint, type checks, unit tests, and baseline visual tests
  pass in light and dark modes.
- **Manual**: macOS and Windows reviews confirm recognizable Lokalite identity,
  readable scaling, keyboard navigation, and platform-appropriate controls.

**Depends on**: Tasks 1.1 and 2.3.

### Task 5.2 — Port vault and project workflows

**Goal**: Provide full manager parity for onboarding, projects, environments,
secrets, imports, policies, activity, preferences, and updates.

**Scope**: Desktop workflows that operate on the broker service.

**Acceptance criteria**:
- **Automated**: component and end-to-end tests cover every primary workflow,
  validation failure, denial state, and empty state.
- **Manual**: a side-by-side macOS walkthrough finds no missing shipped
  capability, and the same workflow completes with native conventions on
  Windows 11.

**Depends on**: Tasks 3.2, 5.1, and 4.3.

### Task 5.3 — Port tray, shortcut, and application lifecycle

**Goal**: Match quick access and background-service behavior on each platform.

**Scope**: Menu bar/system tray, quick actions, global shortcut, single
instance, app activation, lock lifecycle, and launch-at-login where supported.

**Acceptance criteria**:
- **Automated**: lifecycle integration tests cover second launch, broker
  activation, locking, and preference persistence where automation permits.
- **Manual**: menu bar behavior on macOS and tray behavior on Windows pass the
  same capability checklist, including unlock prompts and background clients.

**Depends on**: Tasks 3.3, 3.4, and 5.2.

## Phase 6: Migrate and cut over macOS

### Task 6.1 — Implement preventive first-launch migration

**Goal**: Replace the shipped application without requiring users to export,
recreate, or risk their existing vault.

**Scope**: Existing-install detection, preventive backup, validation,
migration transaction, recovery messaging, and side-by-side prevention.

**Acceptance criteria**:
- **Automated**: synthetic copies of every supported schema either validate and
  open or fail without modifying the original; interrupted migrations recover
  from the preventive backup.
- **Manual**: clean install and upgrades from representative signed releases are
  tested on macOS 14+ using copied test vaults, never the production vault.

**Depends on**: Tasks 2.4, 3.3, 4.4, and 5.3.

### Task 6.2 — Preserve macOS installation identity

**Goal**: Deliver the replacement as a normal update under the existing app,
CLI, configuration, and signing identities.

**Scope**: Bundle identity, paths, entitlements, Developer ID signing,
notarization, CLI package, and installed configuration compatibility.

**Acceptance criteria**:
- **Automated**: release candidates pass signing, notarization, package-content,
  path, and configuration checks.
- **Manual**: an installed Swift release upgrades in place; existing CLI,
  automation, and MCP configuration continue working without re-registration.

**Depends on**: Task 6.1.

### Task 6.3 — Bridge the updater and remove the Swift runtime

**Goal**: Move installed users from the Sparkle-delivered Swift application to
the replacement and leave one supported runtime.

**Scope**: One-time old-feed bridge, replacement updater, rollback guidance,
and removal of obsolete runtime components after the compatibility window.

**Acceptance criteria**:
- **Automated**: update metadata and release artifacts validate, and an update
  fixture proves the bridge selects the intended replacement build.
- **Manual**: a signed installed Swift build updates through the bridge, retains
  its copied vault and settings, and subsequently receives a replacement-app
  update with only one daemon running.

**Depends on**: Task 6.2.

## Phase 7: Productize Windows delivery

### Task 7.1 — Complete Windows desktop integration

**Goal**: Turn the validated Windows prototypes into the production app,
daemon, CLI, and MCP experience.

**Scope**: Windows 11 x64/ARM64 integration gaps, installed paths, activation,
autostart, tray lifecycle, and error recovery.

**Acceptance criteria**:
- **Automated**: Windows integration and end-to-end suites pass for x64 and for
  ARM64 wherever runners support execution; both architectures always build.
- **Manual**: a real Windows 11 system passes the full app, tray, CLI, MCP,
  daemon, Windows Hello, backup-transfer, and restart checklist.

**Depends on**: Tasks 0.3, 3.4, 4.4, and 5.3.

### Task 7.2 — Produce Store-ready MSIX packages

**Goal**: Make Microsoft Store the supported, signed Windows installation and
update channel.

**Scope**: Production x64/ARM64 packages, execution alias, Store metadata,
capability declarations, update identity, and submission evidence.

**Acceptance criteria**:
- **Automated**: both packages validate and install in clean Windows test
  environments; the packaged `lokalite` CLI/MCP binary and desktop application
  report the same version.
- **Manual**: Store certification or its preflight suite passes, and an installed
  package updates without losing its synthetic vault, key, settings, or aliases.

**Depends on**: Task 7.1.

## Phase 8: Qualify and release the multiplatform replacement

### Task 8.1 — Run full automated qualification

**Goal**: Establish one release-candidate quality bar across macOS and Windows.

**Scope**: Rust formatting/linting/tests, frontend lint/typecheck/unit tests,
desktop end-to-end tests, compatibility matrices, packaging, and security
regressions in CI.

**Acceptance criteria**:
- **Automated**: every required macOS, Windows x64, and Windows ARM64 build or
  test job passes from a clean checkout, with no skipped compatibility gate.
- **Manual**: failures and platform coverage gaps are reviewed; no unexplained
  waiver remains.

**Depends on**: Tasks 6.3 and 7.2.

### Task 8.2 — Run real-system migration and security QA

**Goal**: Validate behavior that CI cannot prove on actual supported systems.

**Scope**: macOS upgrade copies and a real Windows 11 system, including system
authentication, tray/menu bar, broker lifecycle, CLI, MCP, MSIX, updates,
backup transfer, and failure recovery.

**Acceptance criteria**:
- **Automated**: the candidate tested manually is byte-identical to the candidate
  that passed Task 8.1 and all collected diagnostics contain no secret values.
- **Manual**: the complete platform checklist passes with no open critical or
  high-severity issue and no production vault is used.

**Depends on**: Task 8.1.

### Task 8.3 — Release and retire the migration line

**Goal**: Publish one stable macOS + Windows product and end public dependence
on the Swift implementation.

**Scope**: Release notes, compatibility notice, macOS channels, Microsoft Store,
support guidance, and roadmap/QA status.

**Acceptance criteria**:
- **Automated**: published artifacts match qualified checksums and update feeds
  resolve to the intended versions.
- **Manual**: a clean install and an existing-user update succeed from each
  official channel; the roadmap records the shipped version and date.

**Depends on**: Task 8.2.
